# Первая версия: история маркетинга и слой покупок

Записка для координатора, 12.09.2026. Это предложение минимального объёма и следующих заданий; приложение ещё не создано. Основание: `КОНСПЕКТ_КЕЙСА.md`, `ДАТАСЕТ.md`, полная речь, сверенная координатором, и официальные технические источники ниже. На 45-й минуте спикер допускает архитектуру без MVP, но прототип даёт больше баллов; пользователь сам выбрал направление рабочей демонстрации. Прогноз и работающая A/B-система для первой версии не нужны.

**Обновление порядка пользователем:** это предварительная архитектурная записка. Прежде любых новых модулей требуются письменные части с правками пользователя, полный PDF, затем GitHub. Задания ниже пока не запускать; актуальная первая часть — `01_ИСТОЧНИКИ_И_АТРИБУЦИЯ.md`, порядок — `КООРДИНАЦИЯ.md`. Публичный сборщик уже существует в `решение/history_collector/`; его повторно не разрабатывать.

## Рекомендация

Первую версию сделать небольшим приложением с загрузкой XLSX, загрузкой публичных публикаций и общей витриной. Бот подходит как дополнительный будущий источник событий, но не решает получение старой истории. Не нужны два отдельных исследовательских проекта: сборщик и анализ сразу используют один формат данных и одно хранилище.

Самый короткий рабочий контур: **источник → сохранённая исходная выгрузка → проверка → SQLite → календарь публикаций и покупок**. Python выполняет импорт и расчёты; один тонкий локальный интерфейс показывает результат и принимает файлы/список каналов. SQLite достаточно для 795 строк покупок и ограниченной истории каналов. Отдельные серверы, микросервисы, очереди, ML и LLM для этого контура не требуются. Выбор конкретной библиотеки интерфейса не должен определять аналитику.

Такой MVP доказывает воспроизводимость получения и обработки доступной истории. Он пока не доказывает, откуда пришёл каждый покупатель и какая реклама вызвала продажи.

## Ровно три способа работы с Telegram

| Путь | Что реально получить | Границы и доступ |
|---|---|---|
| Публичное веб-превью `t.me/s/<username>` | Доступные в превью публикации чужого публичного канала без авторизации: текст/подпись, ссылку и ID поста, дату, ссылки из текста; видимый счётчик просмотров, если присутствует. Сохранять только действительно полученные поля. | Официальный Telegram описывает просмотр публичных каналов через браузер. Это HTML-превью, а не документированный API полного архива: глубину, пагинацию и покрытие периода нужно проверять на конкретном канале. Нет закрытых каналов, индивидуальных просмотров, кликов, расходов или гарантии восстановления удалённых постов. [Официальный анонс веб-превью](https://telegram.org/blog/privacy-discussions-web-bots#view-public-channels). |
| Telegram user-client / MTProto, например Telethon | Историю, доступную авторизованному пользовательскому аккаунту, через `messages.getHistory`; в Telethon — `iter_messages` с датами/ID и пагинацией. Поля сообщения включают текст, дату, entities/ссылки, ID, информацию о пересылке/альбоме/редактировании и доступные агрегатные счётчики. | `messages.getHistory` доступен только пользователям. Публичные каналы можно читать в пределах доступности аккаунту, администраторские права для самой доступной истории не являются обязательным условием. Закрытая/недоступная история не обходится. Нужны собственные `api_id`/`api_hash` и авторизация владельца аккаунта; session не входит в репозиторий. [Telegram: getHistory](https://core.telegram.org/method/messages.getHistory), [Telethon: iter_messages](https://docs.telethon.dev/en/stable/modules/client.html#telethon.client.messages.MessageMethods.iter_messages), [авторизация API](https://core.telegram.org/api/obtaining_api_id), [содержание session](https://docs.telethon.dev/en/stable/concepts/sessions.html). |
| Bot API для будущих событий | Собственные входящие события пользователя, `/start <placement_token>`, нажатия кнопок бота; новые `channel_post` и изменения известных боту постов каналов, где бот состоит. Оплату — только когда она проходит через соответствующую интеграцию либо передаётся отдельным журналом. | Нет метода чтения произвольной старой истории канала. `getUpdates`/webhook получают новые updates, которые Telegram хранит максимум 24 часа до получения. Бот не подключается сам ко всем чужим каналам. Нужен доступ в соответствующий канал; в условиях кейса он не предоставлен. В описании Bot API Message нет счётчика просмотров поста и индивидуальной истории чтения. [Bot API: updates](https://core.telegram.org/bots/api#getting-updates), [какие сообщения получает бот](https://core.telegram.org/bots/faq#what-messages-will-my-bot-get), [параметры запуска](https://core.telegram.org/bots/features#deep-linking). |

Для первой попытки сбора подходит публичное превью: оно не требует настройки аккаунта. Если оно не покрывает нужный период, сохраняем ограничение и решаем, нужен ли отдельный user-client импорт. Не реализуем оба импортёра заранее и не считаем отсутствие веб-превью отсутствием публикаций.

**Просмотры:** счётчик канала приблизительный, включает просмотры пересланных копий и может повторно учитывать человека. Это не уникальные пользователи, клики и тем более не покупки. Полученный сейчас счётчик старого поста — значение на момент сбора, а не на дату публикации. User API имеет `messages.getMessagesViews`; для сбора не использовать увеличение счётчика, то есть `increment=False`. [FAQ о просмотрах](https://telegram.org/faq_channels#q-what-does-the-eye-icon-mean), [метод счётчика](https://core.telegram.org/method/messages.getMessagesViews).

**Удаления и админская аналитика:** удалённый пост исчезает для подписчиков; эти три пути не обещают вернуть его прежнее содержание. Наши ранее сохранённые снимки позволяют сохранить уже полученное, но не восстановить то, чего не собирали. Текущая версия отредактированного поста также не доказывает его прежний текст. Детальная статистика каналов/постов требует соответствующего администраторского доступа и `can_view_stats`; этот источник сейчас отсутствует. [Удаление постов](https://telegram.org/faq_channels#q-what-happens-if-i-delete-a-message), [условия доступа к статистике](https://core.telegram.org/api/stats).

## Минимальный контракт данных

Исходные файлы сохраняются без изменения; для каждого запуска остаются параметры, время получения, хеш и отчёт о покрытии. В SQLite достаточно четырёх основных таблиц; разметку маркетинговых кандидатов можно хранить отдельным небольшим слоем.

| Таблица | Минимальные поля |
|---|---|
| `sources` | `source_id`, публичный URL/username, роль `own_channel / external_candidate / unknown`, URL и фрагмент доказательства связи со школой, статус проверки. Само упоминание не подтверждает платное размещение. |
| `imports` | ID запуска, тип `xlsx / telegram_web / telegram_user`, происхождение `case_dataset / public_observation / synthetic_demo`, источник/путь и SHA-256, `collected_at`, параметры периода, число записей, статус и предупреждения, самый ранний/поздний полученный пост. Ошибка не превращается в «ноль постов». |
| `sale_lines` | Хеш файла + номер исходной строки как ключ, анонимный ID, курс, сумма в копейках, исходное время без придуманного timezone, ID импорта. Исходные 795 строк сохраняются; пара ID+время — только кандидат объединения, не доказанный order ID. |
| `posts` | Ключ канал+message ID, ссылка, дата публикации, текст/подпись, извлечённые URL, доступные `edited_at`/`grouped_id`/сведения о пересылке, nullable счётчики и время их наблюдения, ссылка на исходный снимок и ID импорта. Повторный импорт обновляет состояние, не умножает посты; старые выгрузки остаются в исходных файлах. |

Для разметки: тип `sale / discount / launch / native_candidate / other / uncertain`, доказательный фрагмент, способ `rule / reviewer`, версия правила и статус проверки. Автоматическое правило создаёт кандидата. Разметка содержания не означает установленную рекламную стоимость, контакт покупателя или причинный эффект.

Список исходных каналов задаётся конфигурацией после проверки их связи со школой. Найденные ссылки и пересылки пополняют список кандидатов с доказательствами, а не автоматически превращаются во «все каналы маркетинга». Условные 20 внешних каналов из лекции не являются предоставленным историческим реестром. Нельзя гарантировать полноту сети по открытым ссылкам.

## Что считать и показывать сейчас

- Проверку исходного XLSX: 795 строк, 606 ID, 18 курсов; 04.08–10.09.2026; сумма поля 5 904 671,67. Файл по устному пояснению частично изменён: подпись «сумма данных кейса», без заявления о настоящей выручке школы.
- Покрытие Telegram: какие каналы и даты доступны, сколько постов получено, какие поля отсутствуют, когда сняты счётчики. Отдельный список продажных/нативных кандидатов с прямыми ссылками на доказательства.
- Календарь публикаций и динамику суммы/строк/ID из файла с фильтром по каналам/курсам. Часовой пояс Telegram и неизвестный пояс XLSX не склеивать молча; совместное выравнивание возможно лишь после подтверждения либо с явно показанным сценарным допущением. Крайние дни выгрузки неполные.

Три обозначения результата: **факт** — запись файла или наблюдённый пост с происхождением; **оценка** — классификация/временное совпадение с указанным методом; **неизвестно** — источник конкретного покупателя, расходы, ненаблюдённые касания и эффект рекламы. Временную гипотезу «публикация предшествовала покупке» можно исследовать, но нельзя сохранять как реальное индивидуальное касание. ROMI по каналам остаётся «недостаточно данных», а не 0%. Простейшая будущая доработка — реестр placement ID/расходов + уникальная ссылка или промокод + запись источника в заказе. `/start` доказывает старт бота с параметром, но не каждый просмотр рекламы и не гарантированную оплату.

## Два следующих ограниченных задания

### 1. Разработчику после документирования: воспроизводимый импорт, без интерфейса

**Промпт:** «Ты разрабатываешь только слой импорта первой версии MVP хакатона “Поступашки”. Прочитай согласованный письменный проект, КОНСПЕКТ_КЕЙСА.md и ДАТАСЕТ.md; эта архитектурная записка предварительная. Вход: неизменённый `источники/base.xlsx`, готовые JSONL и снимки сборщика `решение/history_collector/`. Выход: небольшой Python-модуль/CLI импорта XLSX и готовой выгрузки постов, SQLite по согласованному контракту, машинный отчёт о качестве и покрытии, короткий README с точными командами. Публичный сборщик повторно не писать; исходные снимки не изменять. Не используй Telegram-сессии/credentials пользователя, не отправляй сообщения, не собирай участников/личные чаты, не обходи ограничения, не делай UI, атрибуцию, ROMI, ML и автоматический обход всей сети. Критерий завершения: запуск на чистой базе воспроизводит 795/606/18 и контрольную сумму; повторный импорт того же файла и снимков не увеличивает количество записей; каждый пост имеет источник и время сбора; неполное покрытие/ошибка явно отражены; есть небольшие проверки идемпотентности, пропущенных полей и границ дат на сохранённых примерах». Если требуется новая выгрузка, использовать готовый сборщик только по конкретному списку координатора; импорт не должен требовать секретов для демонстрации.

### 2. Аналитику: проверяемая разметка и протокол исторических выводов

**Промпт:** «Ты отвечаешь только за аналитический контракт исторической витрины, не за сборщик и интерфейс. Вход: ДАТАСЕТ.md, ПОЯСНЕНИЯ_СПИКЕРА.md, ПЕРВЫЙ_MVP.md, исходный XLSX и сохранённая выгрузка публичных постов, когда она предоставлена координатором. Выход: компактный markdown с определениями метрик и допустимых выводов; правила кандидатов `sale/discount/launch/native/uncertain`; небольшая CSV-разметка доступных примеров со ссылкой и доказательным фрагментом; набор SQL/псевдокода для проверки витрины. Покажи, какие наблюдения являются фактами, какие оценками, какие вопросы неразрешимы. Разделяй строку, покупателя и предполагаемый заказ; не перераспределяй бандлы повторно автоматически. Не придумывай каналам расходы, покупателям источники, исторические просмотры на дату публикации или связь анонимного ID с Telegram. Не доказывай причинность корреляцией, не строй прогноз/ML и не пиши финальные рекомендации по бюджету. Критерий завершения: каждое правило имеет проверяемый пример и случай неопределённости; определения дают контрольные итоги файла; сравнение времени требует явного timezone; описаны проверки и предупреждения, достаточные разработчику витрины. Если постов ещё нет, подготовь контракт и обозначь недостающий вход, не подменяй его выдуманной историей». 

Координатор после этих результатов принимает формат и запускает отдельное короткое задание на интерфейс поверх готовых импортов/запросов. Так разработчик UI не изобретает трактовку продаж, а аналитик не переписывает сборщик.
