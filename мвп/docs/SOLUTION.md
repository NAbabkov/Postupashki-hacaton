# Решение кейса «Поступашки»

Бизнес продаёт онлайн-курсы для стажировок и работы. Ключевая задача — сохранять связь маркетингового поста с заявкой на конкретный курс и подтверждённой оплатой, затем сравнивать расходы и доход кампаний. Уникальная ссылка определяет источник входа; атрибуционная модель распределяет вклад нескольких входов до оплаты.

## Что реализовано

Календарь хранит пост, кампанию, канал, курсы, даты, ответственного, рекламные расходы и доли бюджета по курсам. Команда выпускает уникальный адрес прямо в карточке, копирует ссылку или текст со ссылкой и вставляет в публикацию. После публикации сохраняет Telegram-адрес поста и меняет статус. Адрес уникальной ссылки не меняется при редактировании поста; повторный выпуск идемпотентен. До публикации вход не активен. После появления переходов источник нельзя перенести в другой канал, курс или кампанию.

Путь: **карточка маркетинга → выпуск ссылки → пост → переход → заявка на курс → подтверждённая оплата → атрибуция → экономика**.

`/r/PLACEMENT_ID` записывает событие `visit` с ID размещения и случайным ID браузера, затем открывает форму внутри приложения. HttpOnly-cookie удерживает этот ID при повторных входах. Форма сохраняет отдельную заявку для пары «посетитель + курс», её первый подходящий источник и событие отправки. Повторная отправка не меняет этап и не дублирует заявку.

Менеджер выбирает заявку и вводит уникальный ID фактически подтверждённой оплаты, сумму и время. Курс и посетитель проверяются по заявке. Дубли ID отклоняются; частичный/полный возврат хранится вместе с исходной оплатой. Интеграция доверенного источника оплат доступна через защищённый `/api/ingest`; она необязательна для демонстрации.

Карточки календаря показывают больше данных: кампанию, курсы, бюджет, состояние ссылки, переходы, заявки и сумму оплат. В раскрытой карточке — ссылка и пост, браузеры, воронка, расходы, ROAS/ROMI и причина отсутствия расчёта. Для календаря/трекинга используется Last Touch с окном 7 дней. Гибкая модель находится на экране атрибуции.

Синтетика независима от истории (seed 20260912). Она включает четыре курса, размещения кампании в разных каналах, альтернативную кампанию одного курса, непокупателей, повторные входы, задержки оплаты, возврат и неизвестный источник. Исходы не принудительно отдаются ML.

## Как работает атрибуция

Для новой оплаты отбираются сохранённые подходящие входы того же посетителя до времени оплаты в заданном окне. Курс должен соответствовать размещению; общий пост может принимать любой курс. Неподходящий курс и будущий вход не участвуют. Повторы одной кампании объединяются: для First Touch — первое касание, для остальных — последнее.

| Модель | Вклад |
|---|---|
| First Touch | 100% первому подходящему входу в окне |
| Last Touch | 100% последнему |
| Linear | Поровну между уникальными кампаниями |
| Time Decay | `score = 2^(-дни / полураспад)`, затем нормировка |

Первая ссылка сохраняет источник заявки и не перезаписывается при повторном входе. Источник оплаты зависит от модели и может отличаться. Например, человек пришёл через кампанию A, потом через B и оплатил один курс: заявка относится A, First отдаёт сумму A, Last — B, Linear — по половине. Time Decay при касаниях за 4 и 1 день и полураспаде 2 дня даёт около 26,1% A и 73,9% B.

Если касаний нет или они вне окна, 100% остаётся «Источник неизвестен». Это не автоматическая органика. В раскрытой оплате видны все 100% распределения и наблюдаемый путь. Сначала рассчитывается полный путь, затем применяются фильтры: выбор двух каналов не превращает их неполную долю в полную выручку.

Для истории применяется отдельное оценочное правило: опубликованный пост предшествует оплате, явно соответствует курсу и находится в окне. Стартовый сценарий — 5 дней, UTC, полураспад 2 дня. Предположения по линейке выключены; при включении условный коэффициент 0,5, не обученная вероятность. Пересылки одного оригинала и равные полные нормированные тексты объединяются в группу объявления; это правило, не восстановленный контакт покупателя.

Для UTC окна 3/5/7 дней дают 143/176/217 подходящих строк из 795, для UTC+3 — 140/165/211. Эти числа показывают чувствительность правила, а не количество доказанных рекламных покупателей. В видео 5 дней приведены как пример, а не обязательный цикл продаж.

## Как учитываются заявки и оплаты

Заявка — интерес посетителя к одному курсу. Один человек может иметь несколько заявок на разные курсы. Повторная отправка формы на тот же курс не добавляет лид. Несколько платежей одной заявки увеличивают сумму, но не число оплаченных заявок.

`CR = оплаченные заявки / все заявки` по первому источнику. В оплатившие попадает заявка с хотя бы одной положительной оплатой после возвратов на этот курс. Этап «Оплачен» нельзя выставить без оплаты. В отчёте атрибуции «доли оплат» — сумма весов положительных транзакций; она может быть дробной. Количество уникальных покупателей — объединение ID, его нельзя складывать по строкам с пересекающимися покупателями.

Поэтому стоимость привлечения лида, стоимость распределённой оплаты и CAC нового уникального покупателя — разные показатели. MVP считает CPL и CPA по модели. Для настоящего CAC требуется определить первого клиента бизнеса, исключить повторные покупки и покрыть все расходы привлечения; исходный кейс этого не позволяет.

## Финансовая модель

Для каждого курса задаются расходы на обучение в процентах суммы после возврата, эквайринг в процентах и фиксированная себестоимость одной оплаты. Рекламные расходы вводятся в размещениях; прочий маркетинг — отдельно один раз на кампанию (креатив, инструменты и т. п.). Нулевая стоимость вводится явно; пустое поле означает неизвестную стоимость.

Обозначения: `R` — распределённая сумма оплат после возвратов; `A` — реклама; `O` — прочий маркетинг; `M = A + O`; `C` — доход до маркетинга после заданных расходов курса.

| Показатель | Расчёт |
|---|---|
| Доход до маркетинга | `C = Σ[R оплаты × (1 − обучение% − эквайринг%) − себестоимость оплаты]`, распределённый весами модели |
| ROAS | `R / A` |
| ROMI | `(C − M) / M × 100%` |
| CPL | `M / заявки первого источника` |
| CPA по модели | `M / сумма долей положительных оплат` |
| CR | `оплаченные заявки / заявки × 100%` |
| Сценарная безубыточная выручка | `M / (C/R)` при положительном `C/R` |

Пример: 10 000 ₽ оплаты, 30% обучение, 2% эквайринг, 500 ₽ себестоимость → `C = 6 300 ₽`. Реклама 5 000 ₽, прочий маркетинг 1 000 ₽ → ROAS 2×, ROMI 5%, результат после маркетинга 300 ₽. Высокий ROAS сам по себе не доказывает прибыль.

Расходы каждого размещения учитываются один раз. Прочий маркетинг кампании делится пропорционально рекламе размещений, если вся она известна и ненулевая; иначе поровну. В посте с несколькими курсами бюджет делится по явно заданным долям. По умолчанию равные доли отмечаются как предположение. При переходе от курса к кампании расходы и распределённые суммы сохраняются; фильтр части курсов не перераспределяет скрытые расходы.

Для исторических кампаний можно задать сценарную оценку общей рекламы; она помечена как оценка и распределяется поровну по размещениям. Это не установленная фактическая стоимость. Обычный исторический ROMI без введённых расходов не рассчитывается.

Полный возврат обнуляет выручку и положительную долю оплаты, фиксированная себестоимость остаётся. Процентные расходы пропорциональны текущей сумме после возврата: реальная невозвратная комиссия отдельно не моделируется. Возвраты хранятся накопленной суммой; дата расчёта отсекает оплаты, но не восстанавливает прошлое состояние возвратов или этапов заявок. Налоги и постоянные расходы компании не распределяются. Этот показатель является маркетинговым ROMI в заданной модели.

ROAS требует известной ненулевой рекламы. ROMI дополнительно требует прочего маркетинга и экономики курса. До истечения срока ожидания после окончания размещения показатели не объявляют отсутствие оплат убытком. Срок ожидания независим от окна атрибуции: один определяет зрелость результата, другой — подходящие касания. Зрелое размещение с нулевыми оплатами и заполненными расходами действительно может иметь −100% ROMI.

## Интерфейс и применение

Основной отчёт — кампания × курс; доступны сводки по курсу, кампании и каналу. Чекбоксы каналов, курсов и кампаний действуют во всех рабочих экранах. Выбор периода означает когорту размещений, до даты расчёта подтягиваются их последующие результаты. Например, два конкретных канала и три курса можно сравнить одним выбором.

Финансовая карточка объясняет полученные оплаты, возвраты, сумму после возвратов, доход до маркетинга, рекламу, прочие расходы и итог. Модели сравниваются при одинаковом бюджете; менять модель не означает менять фактические расходы.

Заявки показаны в воронке по кампаниям/курсам и по этапам менеджера. Журнал оплат хранит связь с заявкой и возвраты. Трекинг показывает адрес каждого размещения, число переходов/браузеров и конверсию. Исторические заявки или клики не выдумываются из факта оплаты.

Для команды из пяти человек: один готовит/проверяет посты и источники, второй ведёт календарь и ссылки, третий проверяет заявки и оплаты, четвёртый заполняет экономику и сравнивает модели, пятый готовит демонстрацию/подачу. Это предложение, имена и окончательные роли добавляются позднее.

## Проверка и пределы MVP

22 тест движка и 17 локальных проверок API подтвердили сохранение денег/весов, строгость курса и времени, раздельность режимов, возвраты, многоканальные фильтры, отсутствие двойного бюджета, зрелость когорты, выпуск/стабильность ссылки, привязку к посту и корректную регистрацию заявки/оплаты. TypeScript проверен; production-сборка выполняется перед публикацией. Исходные файлы имеют сохранённые хеши. Notebook читает подготовленные наборы и результаты проверок.

Данные хранятся в SQLite/D1. Cookie содержит случайный ID браузера; имя, IP и Telegram-профиль не сохраняются. Один браузер не обязательно один человек, другое устройство/удаление cookie могут разорвать путь. Для MVP предполагаем один браузер и передачу ID заявки до оплаты. Приватный опубликованный интерфейс предназначен для демонстрации владельцу; перед реальным рекламным трафиком требуется доступная аудитории входная форма и отдельная авторизация команды.

Атрибуция не доказывает причинный прирост. Для решения о масштабировании нужен контролируемый тест, реальные затраты, фактическая экономика и зрелые оплаты. Платные сервисы не подключались, реальные списания не выполнялись.
