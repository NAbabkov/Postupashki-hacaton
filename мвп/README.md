# Поступашки — маркетинг команды

Операционный календарь, ссылки размещений, CSV-воронка бота и отдельная финансовая атрибуция подтверждённых оплат. Реализованы Calendar v3 и последующая Funnel / Attribution спецификация. Навигация: Календарь / Воронка / Результаты. При переходе из общего календаря приоритет у выбранных live-размещений; демо не скрывает реальную кампанию. Стек: React / Vinext / Vite / Cloudflare Workers / D1.

[Публичный MVP команды](https://demo-komandy-postupili.postupili-demo.workers.dev). Просмотр открыт без аккаунта ChatGPT; изменения и импорт доступны после «Вход команды». Ключ хранится локально в игнорируемом `.env.team-access.txt`, на сервере — в Cloudflare Secret.

## Основной сценарий

1. Войдите как участник команды. Создайте размещение: название, существующая кампания или явно новая, Telegram-канал, один или несколько курсов, плановая дата UTC, рекламный бюджет, необязательный текст. Пустой бюджет означает неизвестные расходы, 0 — бесплатное размещение.
2. В карточке выпустите ссылку. Полный `PUBLIC_APP_URL/r/ID` копируется кликом по адресу. Ссылка и ключ сохраняются; повторный выпуск идемпотентен. После выпуска нельзя менять её кампанию, канал и набор курсов.
3. Вставьте ссылку в Telegram-пост. Публичная публикация обнаруживается по точному адресу в окне от −15 минут до +2 часов к плану. Плановая дата сохраняется, фактическая показывается отдельно. Ручной адрес доступен второстепенно после окончания окна.
4. `/r/ID` записывает `web_visit` с обезличенным ID браузера **до** 302 в `https://t.me/tracker_marketing_bot?start=...`. Опубликованный статус для перехода не требуется. Исторические и отменённые ссылки не работают.
5. Бот команды записывает `start` и `payment_click` в свой `events.csv`. Импортируйте файл через «Импортировать события бота»: сначала предпросмотр, затем подтверждение. Для старого формата даты явно выберите часовой пояс сервера бота.
6. Воронка показывает web-переходы, уникальных запустивших бота, уникальных нажавших «Перейти к покупке», конверсию и отдельно число событий. **payment_click создаёт PurchaseIntent (намерение купить / передача менеджеру), но не Payment и не выручку.**
7. В «Воронке» менеджер регистрирует отдельный подтверждённый Payment: заявка, маскированный userKey, фактически оплаченный курс, сумма, дата UTC и уникальный Payment ID. Заявка однокурсового размещения подставляет курс; многокурсовая требует выбора. Оплату вне бота можно внести только с явным неизвестным источником и без придуманного userKey. Возврат меняет деньги, но сохраняет факт прежней покупки.
8. В «Результатах» выберите модель, окно и группировку. Экономика кампании/курса настраивается отдельно. CRM, Kanban и ручных стадий лидов нет.

«Проверить переход» использует `?preview=1`: не записывает событие/cookie на сайте и передаёт отдельный `test_*` источник боту. Тестовые строки исключаются из CSV-импорта. Не открывайте обычную рекламную ссылку для предварительного просмотра.

## Контракт существующего бота

Фактический код из `bot.py` / `links.py` проверен: UTF-8 base64url без padding, decoder добавляет padding, `source_code` состоит из трёх частей. Бот не запущен повторно и его token не нужен сайту.

Для каждого нового размещения:

```text
source_code = telegram|ASCII_channel_slug|short_botTrackingKey
start = base64url(UTF8(source_code)), длина ≤64
```

`botTrackingKey` — стабильные 10 ASCII-символов, отличающиеся по ID размещения, не номер будущего поста. Длинный source блокируется, не обрезается. Номер Telegram-поста сохраняется отдельно в `postUrl` после публикации. Проверенный старый fixture декодируется в `website|Поступашки|summer_offer`.

Точный CSV, включая порядок 8 колонок:

```csv
timestamp,user_id,username,event,source_code,social_network,channel,content_id
```

Допустимы только `start` / `payment_click`. Для `YYYY-MM-DD HH:mm:ss` требуется явный UTC offset; для ISO-8601 с `Z`/offset время уже определено. Попросите команду бота экспортировать UTC ISO-8601 и сохранять CSV безопасно: исходный экспорт содержит Telegram ID.

Импорт ограничен 2 МБ / 5000 строк. Числовой `user_id` преобразуется в `HMAC_SHA256(BOT_IMPORT_SALT, user_id)`; исходные ID, username и CSV не сохраняются в D1, публичных ответах и логах. При пустом ID допустим только существующий 64-символьный username hash; смена username может разделить идентичность.

`content_id` сопоставляется с `Placement.botTrackingKey` только при полном совпадении канонического `source_code` live-размещения. При расхождении отдельных колонок используется source_code с предупреждением. Неизвестные ключи, старые campaign-level источники и пустой source остаются без размещения. Реальный экспорт не импортируется в demo. ID события = SHA256 нормализованных UTC-времени, HMAC-пользователя, типа события и источника. Повторный импорт не дублирует события; файл с ошибками нужно исправить до commit.

Браузер и Telegram-пользователь индивидуально **не соединяются**: контракт не содержит соответствия. Общая связь — размещение. Уникальная конверсия start → intent = уникальные payment_click-пользователи / уникальные start-пользователи × 100%. Число сырых событий показано отдельно. Заявка → оплата = уникальные оплатившие из наблюдаемой когорты заявок / уникальные пользователи заявок. При отсутствующих start показывается предупреждение; история импорта может быть неполной.

## Атрибуция и экономика

Live/demo: кандидаты для подтверждённой оплаты — **bot start того же userKey**, с известным размещением, совместимым курсом, до оплаты и внутри окна. Browser visit и payment_click не являются финансовыми касаниями. Каждое размещение участвует один раз: earliest start для First Touch, latest для остальных. Нет подходящего start / userKey — вся сумма остаётся Unknown.

История кейса — отдельная сценарная оценка по курсу и времени публикации. Постоянный warning: **«В историческом датасете неизвестно, видел ли покупатель конкретную публикацию. Модель ниже распределяет оплату между совместимыми постами по выбранному правилу и НЕ устанавливает фактический источник покупателя.»** Показываются покрытие совместимыми постами и медиана задержки по парам пост–оплата, без заявления наблюдаемого контакта.

| Модель подтверждённой оплаты | Правило |
|---|---|
| First Touch | 100% первому подходящему касанию в окне |
| Last Touch | 100% последнему |
| Linear | Поровну уникальным размещениям пути |
| Time Decay | Вес `2^(-дни/полураспад)`, нормировка |

Сначала Allocation по placementId, затем кампания / канал / курс / кампания × курс. Два размещения одной кампании сохраняют две доли. Повторные start одного размещения не умножают credit. В истории family_candidate включается явно: base relevance 0,5 для Linear/Decay до нормировки; First/Last выбирают по времени и могут дать гипотезе 100% с маркером низкой уверенности. Неизвестная атрибуция оплаты не считается доказанной органикой. Фильтры применяются после полного распределения; скрытые доли не достаются выбранным каналам. Чекбоксы сохраняют выбор нескольких каналов, курсов и кампаний.

`R` — атрибутированная выручка после возвратов, `A` — реклама, `O` — прочий маркетинг, `M=A+O`. `C` — сумма после переменных расходов обучения, комиссии и стоимости обслуживания оплаты, распределённая теми же весами.

```text
ROAS = R / A
ROMI = (C - M) / M × 100%
CPL = M / заявки
CPA по модели = M / сумма долей подтверждённых платежей (включая возвраты)
CR когорты = уникальные оплатившие пользователи заявок / уникальные пользователи заявок × 100%
```

CPA не означает CAC нового клиента. Неизвестные расходы, экономика, нулевой знаменатель и незрелая когорта дают прочерк. При полном возврате фиксированная стоимость обслуживания остаётся. Общие постоянные расходы и налоги не распределяются. Атрибуция не измеряет причинный прирост.

Реклама суммируется по размещениям, прочий маркетинг — один раз на кампанию. У многокурсового поста бюджет делится по заданным долям, иначе поровну с явным допущением. Сводки: размещение, кампания × курс, курс, кампания, канал. CSV бота не сообщает купленный курс: фильтр курса выбирает продвигающие его размещения, а не доказанную покупку этого курса.

## Хранение и совместимость

Новых SQL-миграций нет: прежняя JSON-таблица D1 workspace_records сохранена. Нормализация на чтении даёт BotEvent и PurchaseIntent view с устойчивым ID по `(mode,userKey,placementId,sourceCode)`; первый payment_click определяет дату. Старый historical userId хранится отдельно как historicalBuyerId, не становится Telegram userKey. Старые Lead records не удаляются, но UI и write actions CRM выключены. Только явно синтетическое старое демо имеет совместимый адаптер касаний; реальные web-переходы никогда не превращаются в bot starts.

Seed демо: 13 размещений, 94 web-события, 150 bot-событий (96 start / 54 payment_click), 66 bot-пользователей и 18 подтверждённых оплат. Повторные, organic и unmapped события добавлены намеренно. Исторические суммы, даты и 795 строк не изменены. Новые локальные/production записи могут увеличивать счётчики поверх seed.

## Публикации, экспорт и доступ

Публичный Telegram HTML: только `t.me/s/<validated username>`, таймаут 7 секунд, до 3 МБ, максимум 2 страницы на канал. Проверка точного канонического `/r/ID` и временного окна; одинаковая ссылка в нескольких постах даёт предупреждение и выбирается ранняя. Ошибка Telegram не ставит статус published. Сканируются только активные pending live-размещения. Приватный канал — ручной ввод с отдельным основанием; если публичный пост доступен, ссылка проверяется.

Открытый календарь у вошедшей команды вызывает защищённый sync раз в 30 секунд. Production Cloudflare Cron — `*/5 * * * *`, работает и при закрытом календаре. Это поиск публикаций, **не автоматическая загрузка events.csv**. Endpoint не принимает произвольных URL.

Экспорт календаря: UTF-8 BOM, `;`, CRLF, кавычки и защита formula injection. Отдельные человекочитаемые колонки кампании, курсов, плана/факта, статуса, бюджета, ссылки/поста, web/бота, подтверждённых оплат/выручки. Сырые JSON, текст поста и идентификаторы пользователей не экспортируются.

Public: `/`, assets, read API, `/r/ID`. Все активные workspace write actions, отдельные Payment/refund endpoints и bot-import — admin session. Старые new_lead/lead/demo actions и /api/visit отвечают 410 после проверки доступа. Cookie подписана серверным secret, HttpOnly, SameSite=Strict, Secure на HTTPS, срок 12 часов. Secret не хранится в JS bundle/localStorage. Trusted `/api/ingest` принимает отдельно INGEST_KEY и подтверждённую оплату с payment_id / purchase_intent_id. `POST /api/payments`, `PATCH /api/payments/:id/refund` проверяют ID, режим, пользователя, курс, дату и сумму; повторный Payment ID отклоняется атомарно. Machine sync — PUBLICATION_SYNC_SECRET или admin session. Публичный read API обезличивает live ID и скрывает заметки менеджеров.

## Запуск и публикация

Рабочая папка репозитория: `мвп/`. Нужны Node ≥22.13, установленные зависимости, Python для `test:api`.

```sh
cp .dev.vars.example .dev.vars
# Замените placeholders независимыми случайными secrets, не коммитьте.
pnpm dev
pnpm typecheck
pnpm test
pnpm lint
pnpm test:api
# После API-проверок очистить только их fixture-ключи:
wrangler d1 execute DB --local --config wrangler.local.json --file tmp/api-cleanup.sql
```

Production: после `wrangler login` создать отдельную D1, зарегистрировать бесплатный workers.dev поддомен, скопировать `deployment/cloudflare.example.json` в игнорируемый `deployment/cloudflare.json`, записать реальный D1 ID и фактический HTTPS origin. Команда `pnpm deploy:cloudflare` собирает Vinext без Sites plugin, применяет миграцию production D1 и публикует Worker с Cron. `--dry-run` проверяет bundle без публикации; `--config-only` готовит `.wrangler/production.json`.

Секреты на Cloudflare: ADMIN_WRITE_SECRET, BOT_IMPORT_SALT, PUBLICATION_SYNC_SECRET, опционально INGEST_KEY. Vars: PUBLIC_APP_URL, TELEGRAM_BOT_USERNAME. Не меняйте публичный origin или HMAC salt после выпуска/импорта без миграции ссылок и идентичностей. Локальные .dev.vars, .env.team-access.txt, secrets JSON, OAuth и production config игнорируются Git.

Отдельная production D1: `postupili-marketing-production`, не local placeholder. Используется прежняя JSON-таблица `workspace_records`. Сайт работает в обычном Cloudflare аккаунте команды, без Sites и ChatGPT-аутентификации. Платный план, собственный домен и подписки не покупались.
